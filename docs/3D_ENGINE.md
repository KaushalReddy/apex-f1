# APEX F1: 3D engine design

**Status (Phase 3): the circuit engine is implemented** (`apps/web/src/lib/circuit`, `apps/web/src/components/circuit`).
**Phase 4 built the procedural car viewer** (section 10), a separate experience from the live circuit. **Phase 5 built the race view**
(section 11): driver markers, interpolation, progress projection and a follow camera on the Phase 3 circuit. Section 6 onward documents what was
built; sections 1 to 5 are the design it follows.

## 1. Coordinate pipeline

```
provider coords (x, y, z in provider units)
  1. scale   : multiply by unitMeters (from circuit_geometry, spike-verified)  -> metres
  2. recentre: subtract centerline centroid (cx, cy, cz)  -> keeps floats small
  3. axes    : three.x = x', three.z = -y', three.y = z' * elevationScale
  4. rotate  : optional yaw about Y for camera framing (default 0)
  -> Three.js world (metres, Y up, right-handed)
```
- Step 3 flips Y to -Z so a map-style top view (x right, y up) looks the same in Three.js.
  Whether the provider frame is right- or left-handed **[VERIFY]**: if the rendered circuit is
  mirrored, fix it here, once, with a single sign.
- `elevationScale` defaults to 1. Any exaggeration is a visible, labelled option, never baked in.
- One pure TS module (`apps/web/src/lib/circuit/transform.ts`) owns this. Components never apply their own offsets.
- A unit test round-trips known points (synthetic) and checks the centerline length is preserved.

## 2. Track
- Input: `CircuitGeometry.points` (closed loop, evenly spaced, already smoothed).
- Mesh: extrude a ribbon along the centerline. Width comes from sourced data; if `widthMeters` is
  null, use a clearly named default constant and show it in the debug overlay (no silent invention).
- Kerbs, pit lane, grandstands: later, only from sourced geometry or obviously generic props.

## 3. Cars on the circuit (Phase 5)
- **Product decision:** drivers on the live circuit are small, translucent, glowing, team-coloured markers (soft glow, brighter core,
  selection ring, hover tooltip, tap-to-select on mobile), never full 3D cars. The procedural cars of section 10 are only for the car viewer.
- State per car: previous sample, next sample, render time. Render time lags real time by a
  configurable buffer (start at 500 ms) so there are always two samples to interpolate between.
- Position: linear interpolation by `sampleT`. Heading: from the interpolated velocity, smoothed
  (slerp) and held when speed is near zero. Stale cars freeze and are visibly marked.
- Never extrapolate beyond the last sample for more than the buffer; show `stale` instead.
- Components planned: `DriverMarker` (glowing marker + number/abbr), `DriverLayer` (wires state to markers), a follow camera. Domain logic stays in `src/domain/`.

## 4. Track progress
Needed for sector/gap displays and for stitching 2D charts to the 3D scene. Project each car to
the centerline with a **windowed** search around its previous index (the spike's whole-line
nearest-vertex search is ambiguous on crossovers such as Suzuka). Output: lap-distance in metres.

## 5. Performance guardrails (measure before optimizing)
- Instanced meshes for 20 cars if draw calls matter; shared materials per team.
- Update car transforms in `useFrame` via refs; no React state per frame.
- Keep the scene static except cars; bake track mesh once.
- WebGL fallback and error boundary in Phase 16.

# Phase 3 implementation (circuit engine)

## 6. Geometry source and format
- **Format:** `packages/contracts/schemas/circuit-geometry.schema.json`, unchanged. `points` are `[x, y, z]` in the **source OpenF1
  location frame, never pre-transformed**. The browser validates every document with `parseCircuitGeometry` (finite numbers,
  >= 3 points, 3-tuples, positive unit, closed flag, required derivation, size cap).
- **Provenance:** artifacts are generated, never hand-drawn: `python spike.py --circuit "Monte Carlo" --export-geometry
  apps/web/src/data/circuits/monaco.geometry.json` (see `apps/web/src/data/circuits/README.md`). Output is deterministic (no
  timestamps, fixed rounding, one point per line) and carries `derivation.sessionKeys`, laps used, sigma/step, the spike verdict
  and `derivation.scale`.
- **z:** median observed car elevation per centerline vertex (flat where unknown). Unreliable where the line crosses itself.
- **Monaco artifact:** `apps/web/src/data/circuits/monaco.geometry.json` is generated by the maintainer with the spike (see
  `apps/web/src/data/circuits/README.md`) from real OpenF1 data. The Phase 3 visual-polish patch deliberately does not touch it. Until
  the file exists in a checkout, `/circuits/monaco` shows an explicit "no geometry generated" state and draws nothing.
- **Loading:** `lib/circuit/load.ts` (server-only) reads `src/data/circuits/<slug>.geometry.json` at build time and passes the
  validated document to the client viewer. A missing or invalid file degrades to the placeholder page.

## 7. Scale caveats (what is and is not claimed)
`unitMeters` is the spike's assumed 0.1 m/unit unless overridden. `derivation.scale.status` is `assumed` (no official length
supplied), `within-tolerance` (measured length within 2% of the official length) or `caveat` (differs by more). The UI shows
"Scale not calibrated" unless `within-tolerance`, labels the measured length "not the official length", and never shows speeds
or distances in physical units. Monte Carlo reports `caveat` (the spike measured a 2.55% difference from the official lap length), so its page shows "Scale not calibrated" together with that percentage. The racing line is shorter than the official lap, so
a few percent of the mismatch may be line-versus-centerline length, not unit error; compare `impliedUnitMeters` across circuits
before treating the unit as global. **Rendering is unaffected:** track and cars share one frame, so a wrong unit changes absolute
size, not relative placement.

## 8. Rendering architecture
```
page (server)  -> loadCircuitGeometry(slug) -> validated CircuitGeometry
CircuitViewer  (client) -> next/dynamic(ssr:false) -> ErrorBoundary -> CircuitScene
CircuitScene   -> <Canvas frameloop="demand"> -> CircuitWorld [ CircuitEnvironment, CircuitTrack, CircuitCamera, {children} ]
```
- **Transform:** `createWorldTransform(geometry)` (see section 1) is created once per geometry and shared through
  `CircuitFrameProvider`. Phase 4 car layers are rendered as `children` and call `useCircuitTransform()`, so cars and track cannot
  disagree. `toWorldInto(out, offset, x, y, z)` is allocation-free for per-frame use. `sameCoordinateSystem()` guards telemetry whose
  `coordinateSystem` differs from the geometry's. Replay frames carry raw OpenF1 x/y/z, which is the same frame, so no backend change is needed.
- **Road:** `lib/circuit/mesh.ts` (pure, unit-tested) builds per-vertex frames once (tangent, left normal, slope-following surface normal,
  lateral room per side) and derives everything from them: the road ribbon (triangles wound +Y; normals follow the slope so the raking sun
  reveals elevation; a gentle height tint), two edge lines (`LineSegments`, about 1 px at any zoom, so they stay visible when the whole
  circuit is in view where a metre-wide strip would be sub-pixel) and a chequered start/finish line at vertex 0 (drawn only when
  `derivation.startFinishAtIndex0` is true; placed with the same transform as the track). On the inside of a tight corner the ribbon is
  narrowed to 90% of the local radius instead of folding over itself. Three draw calls plus ground and grid; no textures, no post-processing.
- **Drawn width (not a measurement):** the road is drawn `max(sourced or 10 m nominal, 1.2% of the circuit's longest dimension)` wide
  (`resolveTrackWidth`), one parameter shared by road, edges and start line. For Monaco that is about 20 m. The page states that the width is
  widened for legibility and that the real width is not sourced. Nothing about the width is verified data.
- **Lighting and colour:** Three.js lights are physically based: a surface lit by total irradiance E shows about `albedo * E / PI`, so dark albedos
  need intensities near PI. The first Phase 3 version (ambient 0.75, directional 1.6, ACES tone mapping, asphalt `#2b313a` on ground
  `#0e1116`) rendered road and ground at nearly the same dark grey, which is why the circuit looked like a faint outline. Now: hemisphere light
  2.2 + raking sun 3.2 (38 degrees, from the south-west), `flat` (no tone mapping), asphalt `#4b5361` against a darker ground, near-invisible grid.
  Contrast between palette entries is unit-tested (`style.test.ts`). No shadows.
- **Camera:** `lib/circuit/camera.ts` fits the circuit exactly: for each centerline vertex (grown by half the drawn road width and 8% padding) it solves
  the distance at which the vertex is inside the frustum for the actual canvas aspect and field of view, and takes the maximum. Overview: 50 degrees
  elevation, 40 degree lens, from +Z so map north is up the screen. Top-down: 89 degrees with a 20 degree lens (orthographic-like, little
  perspective distortion), still fitted. "Reset view" re-applies the overview preset including its field of view and clip planes. After the user
  touches the camera, canvas resizes no longer move it; choosing a preset always applies. Clip planes follow the current distance
  (near = 1%), which keeps depth precision high when the whole circuit is in view and never clips close-up zoom. Orbit, pan, zoom, damping, no
  going below ground, arrow-key pan when the canvas is focused. Tested with a real `PerspectiveCamera` over long, narrow, rotated and irregular
  shapes at aspects 0.5 to 3.5. Follow-car cameras are Phase 4.
- **Performance:** on-demand rendering (no animation loop; Phase 4 switches `frameloop` to `"always"` when cars animate); three.js ships only in a
  lazy chunk loaded by the circuit page; geometry is built once per geometry/width (memoised), with nothing allocated per frame.
- **Failure handling:** missing/invalid geometry -> placeholder page; WebGL or render failure -> `ErrorBoundary` message, page keeps working.

## 9. Known limitations (genuine)
- The visual polish has been verified by unit tests, numeric camera checks and a throwaway CPU preview on a synthetic loop, **not in a real browser or GPU**: lighting, anti-aliasing and the on-screen look of the real Monaco geometry still need a manual check.
- Flat road surface; no kerbs, pit lane, runoff, scenery or elevation validation; the centerline is an averaged racing line, not the track edge.
- Handedness of the OpenF1 frame is unverified: if the rendered Monaco looks mirrored against a known map, set `mirror: true` in the
  one place `createWorldTransform` is called (and record it here).
- The drawn width is a legibility choice, not a measurement (see above); the inside of very tight corners is narrowed rather than drawn at full width.
- Self-crossing circuits (Suzuka) draw correctly as a flat figure-eight but z-fight at the crossing, and the exported z is unreliable there.
  Progress-aware projection is not implemented (not needed until Phase 4+ needs lap progress).
- Index 0 is the timing line only approximately (spike aligns laps within a few points).

# Phase 4 implementation (procedural car viewer)

## 10. Car system
**Scope.** A foundational viewer at `/cars/[team]` for a generic, procedural, F1-inspired car: camera presets, component inspection,
exploded view, an illustrative aerodynamics mode and educational setup profiles. The live circuit (Phase 3 code) is untouched. The full
Car Lab is Phase 8.

**Layers** (`apps/web/src/lib/car`, pure and unit-tested; `apps/web/src/components/car`, React Three Fiber):
| Concern | Where |
|---|---|
| Geometry: lofted superellipse sections (spline-interpolated between authored sections, so surfaces do not kink) with separate top/bottom widths (V-keel chassis, undercut sidepods, airbox), NACA-style wing elements lofted through spanwise stations (curved, twisted front wing; spoon rear wing), lathe tyres with covers, tube halo and swan neck, aerofoil-section suspension links; returned as data-driven mesh specs per assembly | `lib/car/geometry.ts` |
| Illustrative surface pressure (baked vertex colours) | `lib/car/pressure.ts` |
| Component metadata, explodable parts, explode math | `lib/car/components.ts` |
| Team car config + livery, sourced race numbers | `lib/car/teams.ts` (identity reused from `domain/demo.ts`) |
| Specification schema + sourced values | `lib/car/specs.ts` |
| Educational setup profiles, circuit context | `lib/car/setup.ts` |
| Camera presets and fitting | `lib/car/camera.ts` |
| Illustrative flow field, traced streamlines, tip vortices | `lib/car/airflow.ts` |
| Scene, model, aero layer, camera, UI | `components/car/{CarScene,CarModel,Airflow,CarCamera,CarViewer}.tsx` |

**Car space:** metres, Y up, +X forward, origin on the ground at mid-wheelbase. Proportions follow side-view reference renders of the 2026
cars (Red Bull Racing, McLaren, Ferrari, Mercedes) supplied by the project owner, measured at the 3.4 m wheelbase: about 5.0 m long (nose tip
0.94 m ahead of the front axle, rear wing 0.63 m behind the rear axle), a high engine-cover spine (about 0.99 m behind the airbox, 0.87 m at
x = -1.33), a floor edge about 0.1 m up with a large side panel under each sidepod inlet, a tall airbox pod (about 1.1 m), open 8-spoke 18-inch
wheels. The four references share one silhouette (same template), so they justify a better shared body and per-team colour schemes, not
team-specific geometry; every team's provenance stays `generic-procedural`. The reference images are not stored in the repository or bundle. It is not any team's CAD and is not aerodynamically exact.

**Geometry vs livery vs specs.** Every team uses `geometry.variant: "apex-generic-base"` with provenance `generic-procedural`; only colours
and the race number change. A `Livery` has flat colour zones (primary body, engine cover, number fin, wings, airbox pod, halo, rim ring, number),
approximated from the references; no logos, sponsor names or graphics are reproduced (design-system rule). `GeometryProvenance` reserves `configurable-variant` and `team-specific-verified` so real team geometry can be
added later without changing the viewer. Specifications (`CarSpecSheet`) carry status `verified | reported | conflicting | unavailable`, a
source and a season per value; a test rejects any value without a source and any "unavailable" entry with a value. Populated so far:
2026 regulation limits (width, wheelbase, mass, rim diameter; status `reported`, from the FIA's June 2024 announcement) and each team's car
name and power unit (`reported`; Red Bull's power-unit naming is `conflicting`). Everything else is `unavailable`.

**Selection and highlighting.** Each explodable part is one group tagged with its component id; a test asserts every metadata entry is a
real group with meshes and every mesh belongs to exactly one part. Highlighting draws the same geometry again with one shared overlay
material, so no buffers are duplicated. Drags that orbit the camera do not select.

**Exploded view.** One `useFrame` loop moves part groups by `explode * smoothstep(progress)`; base geometry is never mutated. Reduced motion
jumps. The floor and diffuser stay on the ground and the body lifts above them (a part moved below the ground would vanish under the ground
disc; a test forbids negative vertical offsets). Toggling re-fits the camera. Airflow layers are hidden while exploded because the flow is
modelled around the assembled car. A test toggles three times and checks exact reassembly.

**Aerodynamics (illustrative).** Streamlines are traced (RK2) through a hand-built velocity field: potential flow around ellipsoids that stand in
for the nose, chassis, engine cover, sidepods and wheels (doublets, kinematically mapped so lines never enter a body, mirrored in the ground
plane), plus labelled effects for what each device is known to do (front-wing upwash/outwash, faster flow under the front wing and floor,
diffuser and rear-wing upwash, sidepod downwash, a slow wake). Lines are coloured by speed relative to the oncoming air; comet particles move by
travel time, so they visibly speed up under the floor and slow ahead of the nose. Optional layers: surface pressure (vertex colours from textbook
rules: stagnation in front, suction under wings and floor, recovery along the diffuser), helical wing-tip vortices and conceptual force arrows.
Profiles and a conceptual low-drag wing mode change both the drawn wing angles and the field. Everything is labelled illustrative; no
pressures, forces or coefficients are computed or shown. Tests check: free stream far away, no line through bodywork or ground, faster air under
the floor, slower air ahead of the nose, more upwash with more downforce and less in low-drag mode.

**Layout (configurator).** A full-width 3D stage (height `clamp(420px, 100svh - 170px, 780px)` on desktop, width-based on phones) with mode
toggles and camera presets floating over it on larger screens and placed above/below it on phones; a key-figures strip (season, car, power
unit with sourcing status, body, livery); a responsive grid of component cards whose images are renders of the procedural model's own
assemblies, captured in the browser into an offscreen target once per livery/wing change (no image files); a detail row (Inspector + Livery,
Aerodynamics, Setup profile) sized to content; then the specification and regulation tables as expandable panels. A team switcher sits next to
the page heading. Grids use `items-start` so short panels are not padded to the tallest one.

**Rendering.** On-demand frames while static; a continuous loop only during auto-rotate or playing airflow. Lighting is a generated
`RoomEnvironment` (no HDR download) plus a shadow-casting key light and fills, clearcoat paint and soft ground shadows. Camera presets are
solved numerically against a sample of the car's real vertices (assembled or exploded) so every view fills about 90% of the frame at any
aspect (tested); the race number is a small canvas texture (no font download). Geometry, materials and
textures are disposed on change and unmount. WebGL is detected before the scene loads, and an error boundary catches render failures.

**Reference asset.** A local, git-ignored model (`apps/web/public/models/cars/2026_redbull_rb22.glb`, "2026 Redbull RB22" by Dave Love,
Sketchfab, CC-BY-4.0) was used only to sanity-check overall proportions (bounding box). It is not loaded, copied or committed.

**Verified in a real browser (Chromium, Playwright):** desktop 1440x900 and mobile 390x844; three-quarter, side and top presets; exploded view with
labels; aero mode; tap selection on mobile; reduced motion; WebGL disabled. Frame rate was not measured.

**Known limitations.** Generic geometry only; no bargeboards, brake-duct winglets or bodywork cooling louvres; wing angles are illustrative; the
flow field is a teaching model, not CFD; exploded labels are DOM overlays, hidden on narrow canvases, and may overlap at some angles.

# Phase 5 implementation (race experience)

## 11. Race view (`/live`)
**Reuse.** The scene is the unchanged Phase 3 `CircuitScene` (track, fitted camera, lighting) with a `DriverLayer` child inside the circuit's
coordinate frame. Driver identities and team colours come from `domain/demo.ts` (the team UI colours used by cards and markers) and the
sourced 2026 race numbers from the car system; nothing is duplicated. The reduced-motion and WebGL hooks are shared with the car viewer
(`lib/use-client-env.ts`).

**Positioning.** `lib/race/track.ts` builds a path from `centerlineToWorld(geometry, transform)`, the same buffer the road mesh is drawn from.
Progress is the lap fraction along it from vertex 0 (start/finish). `pointAt` maps progress to world, `project` maps world back to progress
with a windowed search around the previous value (safe at crossovers). `lerpProgress` interpolates forward through the line and holds on
backwards noise. `SnapshotBuffer` renders one update interval behind real time so there are two snapshots to interpolate between, and clears
on a new epoch (reset/seek) so cars jump instead of sweeping round the lap.

**Markers.** Compact core plus additive halo in the team colour, kept at a constant on-screen size; thin rings for the selected driver
(white), the leader (gold) and a focused battle (blue); a larger invisible pick target for touch. Transforms are written in `useFrame` (no
React renders per frame); the on-demand scene keeps requesting frames only while playing or following. Labels are DOM elements positioned by
projecting each marker and decluttered by priority (selected, focused, leader, race order). Follow mode moves the existing orbit target with
the selected car.

**Data.** `lib/race/types.ts` is the model every source fills; unavailable values are `null`. `lib/race/providers.ts`:
- `DemoProvider`: the deterministic simulator (`lib/race/demo.ts`). Race distance is a pure function of race time, built from a pace profile
  derived from the centerline's curvature, seeded per-lap noise and one pit stop per car (the car waits on the centerline; the pit lane is not
  modelled). Gaps are exact: the time between the other car and this car passing the same point. Labelled "Demo · simulated" everywhere.
- `ReplayProvider`: stored OpenF1 location frames from the existing API (`/api/sessions/{key}/replay/timeline`), validated
  (`parseReplayFrames`), projected onto the path. Identity is the car number only; race order and timing are shown as unavailable.
- LIVE: the interface is ready (mode `LIVE`, no playback). No provider is configured, so the source switch shows "Live · not connected"
  (disabled) and the header indicator keeps saying "No live session".
Events (`lib/race/events.ts`: overtakes, laps, pit entry/exit, finishes, new battles, session changes) are derived by diffing consecutive
snapshots of the same state, so they always agree with the leaderboard and markers.

**Framing (5.1).** "Fit circuit" (`lib/race/fit.ts`) reuses the Phase 3 `frameCircuit` solver with room for markers and labels, and fits
the circuit into the rectangle left free by any floating panels (`fitInSafeArea`: fit for the safe aspect, scale the distance to the safe
height, shift camera and target together so the circuit centres there). It runs on load, on request, on fullscreen changes and on resize
until the user moves the camera; telemetry never moves the camera. Tested by projecting the real Monaco centerline.

**Labels (5.1).** `placeLabels` (`lib/race/declutter.ts`) is deterministic and draws no leader lines: every label touches its own marker
(right, left, above, below or a corner). In priority order (selected, focused battle, leader, race order) each label keeps last frame's spot
if it is still free (so labels do not hop sides through corners), else takes the first free spot; failing that it tries a compact code-only
form, then hides until there is room. The selected driver's label is never hidden. Spots must stay inside the canvas and clear every marker
core and placed label. Markers are projected with the render camera every frame, so labels cannot drift.

**Events (5.1).** Generated by the provider on a fixed 1 s session-time grid (identical at every playback speed), with battle hysteresis
(start at 0.8 s, end above 1.2 s; none on lap 1). A reset, seek or restart rebuilds the history to that moment instead of appending.

**Immersive mode (5.1).** "Fullscreen" puts the race theater container into native fullscreen (Fullscreen API), or a fixed full-viewport
in-page layer when the API is unavailable or refused (Escape leaves it; page scroll is locked meanwhile). The 3D stage is always the
container's first child, so switching never remounts the scene or creates a second WebGL context. Floating translucent panels (session,
toolbar, race order, driver details, events, playback) sit in a pointer-transparent layer so the circuit can be dragged between them; on
phones they become one bottom sheet at a time. The app-wide `page-in` entrance animation now uses `backwards` fill so its wrapper keeps no
transform afterwards (a transform made it the containing block for fixed overlays).

**Known limitations.** Only Monaco has geometry. The replay window is the existing 10-second sample, needs the API running, and the API's CORS
configuration must allow the web origin. Pit lane, track limits, sector times, tyres and weather are not modelled. Labels can still crowd when
many cars are nose to tail; the selected and leading drivers always keep theirs.
